# Motion Studio

A personal, **local-first** screen recorder. Record your screen, and it zooms
with smooth framing — following the cursor automatically, or on zoom moments you
place by hand — lets you trim non-destructively, and exports shareable
H.264/WebM videos, plus a poster frame, transcript and Markdown summary. Built
with Tauri 2, React, TypeScript, ffmpeg and SQLite.

Everything runs on your machine. There are **no accounts, no billing, no
telemetry, no analytics, and no hosted control plane**.

## Quick start (one command)

Prerequisites, installed once:

- **Node 22.13+** (required by current pnpm; `pnpm first-run` refuses to start
  on older Node with a version error)
- **ffmpeg** on your `PATH`
  - Windows: `winget install --id Gyan.FFmpeg -e`
  - macOS: `brew install ffmpeg`
  - Linux: `sudo apt install ffmpeg`
- **Rust toolchain** (to build the desktop shell): <https://rustup.rs>
  - On Windows also install the **MSVC C++ build tools** (Desktop development with C++).

Then:

```bash
pnpm first-run
```

`pnpm first-run` runs `scripts/bootstrap.mjs` (checks the tools above and
installs JavaScript dependencies), then launches the desktop app.

The scripts below use pnpm, but nothing in the build requires it — Tauri's
`beforeDevCommand`/`beforeBuildCommand` invoke the local binaries through
`npx --no-install`, so npm and yarn work the same. This also keeps the desktop
app startable when a package-manager policy (for example pnpm's
`minimumReleaseAge`) would reject re-running an install mid-build.

Other useful scripts:

```bash
pnpm dev         # UI only, in a browser (no recording/export — desktop app needed)
pnpm test        # unit tests + real-ffmpeg end-to-end tests
pnpm typecheck   # TypeScript type checking
pnpm build       # typecheck + production web build
```

> The browser dev server is for UI work. Recording, saving, and export require
> the desktop app. In the browser the missing pieces surface as clear,
> recoverable messages instead of failing silently.

## How it works

```
React webview (capture + edit UI)
        │  MediaPorts / Transcriber
        ▼
Pure TypeScript core  (src/core)         ← all media planning logic
        │  ffmpeg argv, no OS access
        ▼
Tauri (Rust) platform layer (src-tauri)  ← OS integration
   • SQLite project store        • runs local ffmpeg/ffprobe (validated argv)
   • recording session + timer    • cursor sampling
   • system tray (stop)           • filesystem + clipboard + reveal
```

- **UI**: React + TypeScript. Screen/window capture uses the browser
  `getDisplayMedia` (the OS shows its own picker) and `MediaRecorder`.
- **`src/core`**: pure, dependency-free logic — trim math, cursor clustering,
  zoom keyframes (cursor-driven and manual), the ffmpeg filtergraph, presets,
  Markdown, validation.
  It is the single source of truth and is fully unit-tested.
- **Pipeline**: `src/core/pipeline.ts` orchestrates the render, poster,
  transcript and summary. It runs identically against the Rust ports (in the
  app) and the Node ports (in tests).
- **`src-tauri`**: Rust owns everything the webview must not: SQLite, process
  execution, tray, and cursor sampling. The webview can only ask it to run
  `ffmpeg`/`ffprobe` with argv that passes validation.

### The render graph (single source of truth)

`trim → fps → optional crop → optional cursor highlight overlay → smooth
zoompan (output at canvas size, so no aspect distortion) → scale-to-fit →
pad → rounded framing → optional callouts → yuv420p`, then packaged by the
chosen preset (H.264/MP4 or VP9/WebM). Poster, transcript and Markdown are
written next to the video.

Rounded framing is four small background-coloured corner wedges overlaid on the
content, generated by the dependency-free PNG encoder in `src/core/png.ts`.
Masking the whole frame with `geq` was measured at ~5x the cost of the entire
rest of the render, so it was dropped. The content's fitted size and offset are
computed in TypeScript (`fitInside`) rather than by
`force_original_aspect_ratio`, so the wedges land on exact pixel coordinates.

Cursor timestamps are **clip-relative**: `toClipTime` rebases the recorded track
onto the trimmed timeline before the plan is built, because the overlay runs
after `setpts=PTS-STARTPTS`. Zoom keyframes use the same convention, so the
highlight and the zoom stay in sync when the trim does not start at zero.

Zoom keyframes come from one of two sources, selected per project:

- **Cursor** — clusters the recorded cursor track into zoom moments.
- **Manual** — hand-placed stops (`src/core/zoom.ts`). A stop is *when*, *how
  far in*, *where*, and *for how long*; it expands into the same ease-in / hold
  / ease-out keyframes a cursor cluster does, so there is a single render path.
  Stops are stored in **source** time, like the trim, so they keep pointing at
  the same frame when the trim moves; overlapping holds are resolved by
  shortening the earlier stop.

Both sources feed `withZoomTimeline`, which is re-run on every trim or zoom
edit. Switching modes keeps both sources, so it is lossless.

## Configuration

Copy `.env.example` to `.env` (gitignored) to override defaults:

| Variable | Purpose |
| --- | --- |
| `FFMPEG_PATH` | Explicit ffmpeg binary (otherwise auto-detected: env → PATH → winget) |
| `FFPROBE_PATH` | Explicit ffprobe binary |
| `WHISPER_CPP_BIN` | Path to a local `whisper.cpp` binary (enables transcription) |
| `WHISPER_MODEL` | Path to a local whisper model (e.g. `ggml-base.en.bin`) |

Secrets and machine-specific paths live only in `.env`, which is never
committed. Transcription is entirely local and optional: if it is not
configured, exports still succeed and simply skip the transcript.

## Where your data lives

Recordings, exports and the SQLite database are stored in the OS app-data
directory:

- **Windows**: `%APPDATA%\com.local.motionstudio`
- **macOS**: `~/Library/Application Support/com.local.motionstudio`
- **Linux**: `~/.local/share/com.local.motionstudio`

```
com.local.motionstudio/
  motion-studio.sqlite       # project records (paths, trims, zoom, callouts)
  recordings/               # original captures (never modified)
    exports/                # rendered videos + posters/transcripts/summaries
```

**Backup**: copy the whole directory. To restore, put it back in place — the
app reads everything from there. Nothing is stored anywhere else.

## Platform notes

### macOS screen recording & microphone permission

The first time you record, macOS asks for **Screen Recording** and
**Microphone** access:

1. **System Settings → Privacy & Security → Screen Recording** → enable the app.
2. **System Settings → Privacy & Security → Microphone** → enable the app.
3. Quit and reopen the app — macOS requires a restart after granting screen
   recording.

Cursor sampling and the global tray "Stop" behave per-OS; where a permission is
missing, the UI reports it instead of failing silently.

### Windows

ffmpeg installed via winget is auto-detected even if it is not on `PATH`. The
first run in a fresh terminal may need `FFMPEG_PATH` if `PATH` has not refreshed.

Cursor sampling uses `GetCursorPos`, with the primary display's physical pixel
size from `GetSystemMetrics`. Tauri marks the process per-monitor DPI aware, so
both agree. Samples taken while the pointer is on a secondary monitor are
dropped rather than clamped, so auto-zoom never jumps to an edge.

### Linux

Install `ffmpeg` from your distro, plus `xdg-utils` for "reveal in folder".

Building also needs the PipeWire headers and clang's bundled headers, because
screen capture is compiled natively here (see below):

```bash
sudo apt install libpipewire-0.3-dev libclang-common-21-dev
```

**Screen capture is native on Linux, not done by the webview.** WebKitGTK hands
out a display track that encodes to zero frames and whose frames read back solid
black through both a 2D canvas and WebGL — measured on the saved file, which
reported limited-range black (`YAVG=16`) on every frame. Nothing in JavaScript
fixes that, so Rust records instead: it asks `xdg-desktop-portal` for a
ScreenCast session (the compositor shows its own picker), consumes the PipeWire
stream, and pipes the frames to the same local ffmpeg everything else uses. The
portal path also gets two things the webview never did — window capture, and a
visible mouse pointer, which the compositor bakes into the frame.

Windows and macOS keep recording in the webview with `getDisplayMedia` +
`MediaRecorder`; the backend reports which recorder to drive, so the choice is
never sniffed from a user agent.

Cursor sampling needs **X11**: `libX11` is loaded at runtime (`dlopen`), so no
X11 headers are needed to build and the binary still starts without X11.

**Wayland deliberately does not expose the global cursor position to
applications**, so cursor-driven zoom has nothing to follow there. The app
detects this, reports it on the recording screen, and records normally —
everything else (trim, crop, padding, rounded framing, callouts, export) works
unchanged.

On Wayland, use **manual zoom** (Zoom → Manual in the editor): play to the
moment you want, add a zoom, then click the preview to aim it. It produces the
same keyframe timeline cursor zoom does, so the render path is identical. An
X11/Xorg session is only needed if you want the zoom placed for you.

> XWayland is not a workaround: `XQueryPointer` succeeds there but returns a
> frozen position, which is worse than failing — the zoom would silently pin to
> one wrong point for the whole video. The app refuses it on purpose.

## Privacy

- No network calls, no analytics, no crash reporting, no auto-update pings.
- All rendering uses your local ffmpeg; all transcription (if enabled) uses your
  local whisper.cpp.
- The only files written are your recordings, exports and the local database
  under the app-data directory above.

## Development

```bash
pnpm install
pnpm typecheck
pnpm test         # unit tests + E2E (E2E requires ffmpeg on PATH)
pnpm tauri dev    # run the desktop app (after Rust is installed)
```

Rust-side checks (after installing Rust):

```bash
cd src-tauri
cargo test
cargo build
```

The TypeScript core is where the interesting logic lives and is covered by the
test suite; the Rust layer is intentionally thin and validated.
